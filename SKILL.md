# rea-vm

## Purpose

Turn a reverse-engineering question into an auditable pipeline:

```text
scope -> capability matrix -> REA static analysis -> authorized VM execution
-> dynamic observations -> IDA evidence -> graded report -> cleanup
```

The skill is a coordinator, not a promise that every engine exists. Each stage
must probe the current environment, state its status, and either run, degrade,
or stop with a diagnosis.

## When to use

- REA has produced a hypothesis that needs real execution evidence.
- A user explicitly authorizes analysis inside a disposable VM.
- Static findings must be separated from runtime observations.
- The deliverable needs real IDA or IDA MCP screenshots and a structured report.

Do not use it for unauthorized targets, production systems, or to run a
suspicious sample merely because a file looks interesting.

## Non-negotiable boundaries

- Confirm authorization and scope before any execution.
- Prefer a disposable VM with a snapshot taken before driver loads, boot
  configuration changes, or sample execution.
- Never place credentials, private keys, tokens, or personal paths in the
  skill, logs, reports, or command history.
- Do not modify real EDR, `ntfs.sys`, `classpnp.sys`, or a production volume
  stack.
- Do not claim a tool ran, a screenshot exists, or a report was generated by a
  specific engine unless that was observed.
- Label every conclusion as verified fact, strong inference, unverified
  hypothesis, or blocked-by-environment.

## Runtime model

On every invocation, run the preflight probe before choosing a path:

```text
scripts/preflight_check.py --json
```

Windows wrapper:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\preflight_check.ps1
```

Use the resulting matrix to classify each dependency:

| Status | Meaning | Action |
|---|---|---|
| supported | Present and callable | Use it |
| unsupported | Present but this host/OS cannot run it | Route elsewhere |
| unavailable | Not installed or not configured | Degrade or stop that stage |
| unknown | Probe could not establish state | Do not assume success |

Read `references/environment-checks.md` for probe details and expected
artifacts.

## Standard workflow

### Phase A - scope and parameters

Resolve from existing configuration first; ask only when a missing value would
materially change the result. Never guess hosts, users, credentials, target
paths, or authorization.

Minimum parameter set:

```yaml
target:
  path: <local sample or artifact>
  sha256: <expected digest>
  goal: <question to answer>
vm:
  host: <address>
  user: <account>
  key: <path to key on the operator machine>
  vmx: <hypervisor config path, optional>
  snapshot: <snapshot name, optional>
evidence:
  root: <output directory>
report:
  format: <paperjsx-pdf|paperjsx-docx|markdown>
```

See `examples/example-config.yaml`. Values are examples; they are not defaults.

### Phase B - preflight and capability matrix

Probe, do not assume:

1. Host OS, architecture, shell, working directory, repository state.
2. REA entry point, version, provider candidates, and callable operations.
3. SSH client path, target reachability, key-based auth, and whether the
   `ssh` on `PATH` is a wrapper or shim.
4. IDA installation, IDA MCP bridge, and whether screenshots are genuinely
   available.
5. PaperJSX package/API availability and output directory writability.
6. VM state, snapshot presence, disk space, and required debugging tools.

Write the matrix to `<evidence>/metadata/capabilities.json`. Distinguish
blocking gaps from optional ones.

### Phase C - REA static analysis

Use the REA interface that is actually present. Inspect
`binary_session`/provider candidates before opening a target. Preserve version,
input hash, Evidence IDs, and raw output. Convert findings into testable
hypotheses; do not turn decompiler text into runtime claims.

Read `references/workflow.md` for provider routing and evidence capture.

### Phase D - SSH to the authorized VM

- Prefer key auth and a least-privilege account.
- Resolve the real client path; a `PATH` shim that prints a fixed string is not
  a working SSH client.
- Verify with a read-only command before any state change.
- Transfer samples and scripts with SFTP/SCP; verify hashes on both sides.
- Prefer uploading a `.ps1`/`.sh` and executing it by file path over long
  inline command strings with nested quotes.
- Put timeouts, exit-status checks, and cleanup around every remote action.

Read `references/troubleshooting.md` for channel, quoting, and packaging
failures observed in practice.

### Phase E - dynamic execution and debugging

Turn static hypotheses into a debug plan: breakpoints or probes, expected
observations, functional checks, negative controls, and restore steps.

- Select only debuggers that probe as available.
- Record process/module/thread/register/stack/memory state only to the extent
  the tool actually supports.
- Keep observation, inference, and tool output distinct.
- Set time and resource limits; snapshot before boot-config or driver changes.
- If execution would require new authority, stop and ask.

### Phase F - IDA and screenshot evidence

Discover the IDA surface before using it:

- REA may expose an `ida` provider only when configured. Check
  `binary_session`; do not assume the provider exists because the IDA
  application is installed.
- If using `ida-pro-mcp`, verify the package, plugin, and configuration.
- For GUI screenshots, capture the actual application window from the same
  interactive session. A screenshot of a terminal, a synthetic image, or a
  placeholder is not an IDA screenshot.
- For headless analysis, write real decompiler output to a file and cite the
  exact command; do not call a text file a screenshot.
- Record path, timestamp, address/function, purpose, and which conclusion the
  image supports.

Read `references/evidence-and-reporting.md` for the capture and validation
rules.

### Phase G - evidence normalization

Use this logical layout unless the project has a stronger convention:

```text
<evidence>/
  metadata/        environment, versions, hashes, capability matrix
  static/          REA and IDA static output
  dynamic/         SSH/VM command output, probes, event logs
  dumps/           memory images and derived artifacts
  screenshots/     real captured images
  report/          final report and referenced assets
```

Every claim links to evidence. Keep "not executed", "blocked", and "unknown"
visible instead of smoothing them into success.

### Phase H - PaperJSX report

Probe the actual PaperJSX surface first:

- MCP tools such as `generate_report`, `generate_report_docx`, or
  `generate_presentation`, if connected.
- Otherwise the `@paperjsx/json-to-pdf`, `json-to-docx`, or `json-to-pptx`
  packages, if installed.

Validate the JSON shape against the installed version's schema. Generate the
artifact, confirm the file exists, is openable, and references existing
images/tables. If PaperJSX is unavailable, produce a Markdown report using
`templates/experiment-report.md` and state the degradation explicitly.

### Phase I - cleanup and handoff

- Revert the VM snapshot or stop temporary services when safe.
- Remove temporary install tasks, servers, and test credentials.
- Do not delete the sample, original evidence, or uncommitted user work.
- Run syntax/structure checks on the skill and record which tests were real,
  simulated, or not run.
- Report the exact skill path, invocation, capability matrix, and remaining
  unknowns.

## Decision rules

- **No authorization** -> static-only; stop before execution.
- **No snapshot** -> create one or stop before driver/boot changes.
- **No SSH but a hypervisor console exists** -> use the console for bootstrap;
  do not pretend SSH succeeded.
- **No IDA MCP** -> use REA/Ghidra or headless IDA, and label the evidence
  source accordingly.
- **No PaperJSX** -> Markdown fallback, explicitly marked.
- **A probe returns unknown** -> treat the stage as blocked, not passed.
- **A tool call times out** -> preserve partial output, diagnose, and do not
  retry blindly.

## Completion criteria

Do not claim completion until the final report states:

1. Which context and artifacts were actually read.
2. Which stages ran, were simulated, were not verified, or were blocked.
3. The capability matrix and its evidence.
4. The exact evidence, screenshot, and report paths.
5. The skill location and how to invoke it.
6. Remaining risks and unknowns.
